# Tokyo Nebula — Repo Split Design

**Date:** 2026-05-27
**Branch:** `feat/repo-split` (to be created off `main` after `feat/tokyo-nebula-port` lands)
**Status:** Design

## Summary

Split the current monorepo into two repositories so each can be published to its appropriate registry:

- **`tokyo-nebula`** (existing repo, restructured) — VS Code extension. Holds the source theme JSONs, the build script that generates a Zed-compatible family file, and the committed generated artifact under `dist/`.
- **`tokyo-nebula-zed`** (new repo at `github.com/juanarrow-io/tokyo-nebula-zed`) — Zed extension. A six-file distribution shell with `extension.toml` at the root, the generated `themes/tokyo-nebula.json`, README, and LICENSE.

Sync between repos is manual: after palette changes in `tokyo-nebula`, regenerate via `node scripts/build.mjs`, then copy `dist/tokyo-nebula.json` to `tokyo-nebula-zed/themes/tokyo-nebula.json` and commit there.

## Goals

- Make `tokyo-nebula-zed` submittable to the official Zed extensions registry, which expects `extension.toml` at the repo root.
- Slim the VS Code `.vsix` package by removing Zed artifacts and development docs from what `vsce package` bundles.
- Keep design docs (`docs/`) local-only — preserved on disk for future sessions but no longer tracked in git.
- Maintain a single source of truth for palette values (`tokyo-nebula/themes/*.json`) — `tokyo-nebula-zed` carries only the generated derivative.

## Non-goals

- No automated cross-repo sync. The user explicitly chose manual sync; CI/GitHub Action automation is out of scope.
- No history preservation for the new repo. `tokyo-nebula-zed` starts with a fresh `git init`; the granular history of how the Zed port was built lives in `tokyo-nebula`.
- No build script changes beyond path adjustments. The resolver logic, mapping tables, and test fixtures remain identical to what's currently in `zed-extension/scripts/build.mjs`.
- No version bump on either repo. Both stay at their current versions (`tokyo-nebula` at `0.1.0`, `tokyo-nebula-zed` initializes at `0.1.0`).

## Prerequisite

`feat/tokyo-nebula-port` must merge to `main` of `tokyo-nebula` before this work begins. The split work then branches off `main` as `feat/repo-split`. This spec assumes that prerequisite is complete.

### 2.2 Adjust paths in `scripts/build.mjs`

Current `main()` (in the previous `zed-extension/scripts/` location):

```js
const scriptDir = dirname(fileURLToPath(import.meta.url));
const repoRoot = resolve(scriptDir, '..', '..');

const outDir = join(scriptDir, '..', 'themes');
```

New `main()` (in `scripts/`):

```js
const scriptDir = dirname(fileURLToPath(import.meta.url));
const repoRoot = resolve(scriptDir, '..');
const themesDir = join(repoRoot, 'themes');
const outDir = join(repoRoot, 'dist');
const outFile = join(outDir, 'tokyo-nebula.json');
```

Three lines differ: `repoRoot` walks up one level instead of two; `outDir` resolves to `<repoRoot>/dist` instead of `../themes/`; `outFile` derived from new `outDir`.

Tests that resolve the themes directory via `resolve(here, '..', '..', 'themes')` (walking up two levels from `zed-extension/scripts/`) become `resolve(here, '..', 'themes')` (walking up one level from `scripts/`).

Each instance of `resolve(here, '..', '..', 'themes')` becomes `resolve(here, '..', 'themes')`.

### 2.9 Add optional sync helper `scripts/sync-zed.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

# Regenerate the Zed family file and copy it into a sibling tokyo-nebula-zed
# checkout. Assumes the layout:
#   ~/Tools/tokyo-nebula/      (this repo)
#   ~/Tools/tokyo-nebula-zed/  (sibling)

REPO_ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
ZED_REPO="$(cd "$REPO_ROOT/.." && pwd)/tokyo-nebula-zed"

if [ ! -d "$ZED_REPO" ]; then
  echo "error: expected tokyo-nebula-zed at $ZED_REPO" >&2
  echo "       clone it as a sibling of this repo first." >&2
  exit 1
fi

node "$REPO_ROOT/scripts/build.mjs"
cp "$REPO_ROOT/dist/tokyo-nebula.json" "$ZED_REPO/themes/tokyo-nebula.json"

echo "synced -> $ZED_REPO/themes/tokyo-nebula.json"
echo "next: cd $ZED_REPO && git add themes/ && git commit && git push"
```

Made executable (`chmod +x scripts/sync-zed.sh`).

## Section 4 — Sync workflow (post-split)

Whenever palette source themes change in `tokyo-nebula`:

```bash
# In tokyo-nebula
node scripts/build.mjs                 # writes dist/tokyo-nebula.json
git add dist/tokyo-nebula.json
git commit -m "build: regenerate Zed family"
git push

# Then sync to the Zed repo
./scripts/sync-zed.sh                  # copies dist/ → ../tokyo-nebula-zed/themes/
cd ../tokyo-nebula-zed
git add themes/tokyo-nebula.json
# bump version in extension.toml if shipping a new release
git commit -m "sync: regenerate from tokyo-nebula <short-sha>"
git push
```

No tests run in `tokyo-nebula-zed`. The repo is verified by manual install in Zed.

## Open risks

- **VS Code marketplace publish requires a `publisher` field.** The current `package.json` has the field removed (deferred from the earlier author cleanup). After the split, publishing to the marketplace remains blocked until a publisher is added. Acceptable — the split doesn't make this worse, and the user already chose to defer.
- **Zed registry submission requires a versioned release tag.** After the initial push of `tokyo-nebula-zed`, submitting to `zed-industries/extensions` will require a git tag matching the `extension.toml` version. The implementation plan will include the `git tag v0.1.0 && git push --tags` step.
- **The sync helper assumes a fixed sibling layout.** `~/Tools/tokyo-nebula/` and `~/Tools/tokyo-nebula-zed/` must be siblings for `scripts/sync-zed.sh` to find the target. Documented in the script comment; if the user moves either checkout, the script breaks loudly (not silently).
- **`docs/` becoming untracked** means future Claude sessions that read it via `git log` won't see new design docs at all — they exist only on disk. Acceptable: the user already runs Claude with full filesystem access; sessions read `docs/` directly from disk.

## Out of scope

- VS Code marketplace publication.
- Zed registry submission (creating the PR against `zed-industries/extensions`).
- GitHub Actions automation of the sync flow.
- Renaming variants further.
- Adding new variants.
- Light-theme variants.
